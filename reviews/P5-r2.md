### SL-P5-r2-E1: a resumed stage keeps partial rows made by other code or another agent version

- **Evidence:**
  - `harness/main.mjs` `runStage` (the `prior` loop under `const prior = new Map()`) resumes any partial row whose `stage` and `split` match and whose artifact exists.
    - It never compares the row's `agent_version`, model `runtime`, or the code that produced its labels against this dispatch.
  - The round 2 design makes this likely:
    - each dispatch is a fresh checkout, and a session commits the partial file between dispatches;
    - DECISIONS.md (r2) names "a harness change between dispatches would make resumed rows differ from new ones" as the reason to reverse.
    - Nothing enforces that, and P5 rounds edit `harness/` and `src/` between dispatches; round 2 itself did.
  - The box already runs two `claude` versions: 2.1.322 for `forge-runner` (forge/eval comment) and 2.1.330 for the login user (`results/preflight.jsonl`).
  - Section 6, item 1: E0 runs "before any tuning". `contracts/eval.md`: "Later rows never overwrite E0".
    - A resumed E0 can hold rows labeled by the code at commit A, and rows labeled by tuned code at commit B, in one frozen file.
    - Section 6, item 4 (pinned revisions) breaks the same way for the agent version.
  - The checkout is shallow (forge `eval.yml`, `actions/checkout` with the default depth), so a row's `git_sha` cannot be diffed against HEAD on the box.
- **Probe on `1d62f49`:**
  - The round 3 test `main: a partial run made by other code or another agent version is run again, not resumed`, with its `code_hash` assertions removed, changes the committed partial row's `agent_version` to `scripted 0.0.1` and dispatches again at a new sha.
  - The old run is resumed:

    ```
    AssertionError [ERR_ASSERTION]: agent_version: the run is made again at this commit
      actual: 'e0-scripted-sl06-changelog-wrong-path-A-k1-2222222'
    ```
- **Fix (applied in r3):**
  - Each row carries `code_hash`, a sha256 over the files the runs depend on: `harness/` (less `stages.json`), `src/`, `oracle/` and `fixtures/` (less `*.test.mjs`), `contracts/claim-judge.md`, `contracts/split.json` and `models.lock`.
  - A partial row is resumed only when its `code_hash`, `agent_version`, `runtime` and `model_revision` match the current dispatch. Any other row is run again at this commit.
  - The summary note counts the runs not resumed.
  - The new test fails on `1d62f49` (`every row records the code it ran`) and passes on r3.

### SL-P5-r2-E2: the tolerance median's filter is still undocumented (carries SL-P5-r1-E6)

- **Evidence:**
  - `harness/score.mjs:55`: `t1.per_repeat.map((p) => p.gt_sf).filter((n) => n > 0)`.
  - `contracts/eval.md` gives no filter.
  - Round 1's fix was "follow the contract literally, or write the reading down in DECISIONS.md". Round 2 did neither.
- **Why minor:** the filter matters only when a repeat has no silent failures. Such a repeat has no recall, so it is already outside `[min, max]`.
- **Fix (applied in r3):** a DECISIONS.md line gives the reading. Under the literal reading, the median would be 0 in sparse runs, and 1 / 0 has no meaning.
